# LAB2. Агент для cleanbot-ops

## 1. Цель

Добавить в проект LLM-агента, который управляет парком роботов на естественном языке: оператор пишет «Запусти уборку у cleanbot-01», агент сам решает, какие инструменты вызвать, и выполняет команды через REST API симулятора.

## 2. Стек и конфигурация

| Компонент | Выбор |
|---|---|
| Язык / сборка | Kotlin, Gradle-модуль `agent/` |
| HTTP-клиент | Ktor Client (CIO) |
| LLM | **qwen3:4b-instruct** (≈2.5 ГБ), запускается локально через **Ollama** |
| API модели | нативный `POST /api/chat` Ollama с параметром `tools` |
| Стоимость | **0**: модель работает на локальной машине, ключей и оплаты за токены нет |
| Железо | Windows 11, NVIDIA RTX 5080 (16 ГБ VRAM), JDK 17 |
| Контекст | `num_ctx = 8192` |

Настройки лежат в `agent/.env` (в `.gitignore`, в репозиторий не попадает):

```
OLLAMA_URL=http://localhost:11434
MODEL=qwen3:4b-instruct
SIMULATOR_URL=http://localhost:8080
```

Почему локальная модель: платные API не нужны, а для задачи «выбери один из двух инструментов» хватает маленькой модели. Qwen3 4B выбрана за поддержку нативного вызова инструментов (gemma3 и phi4 их в Ollama не поддерживают) и малый размер.

## 3. Реализация

Код: `agent/src/main/kotlin/Agent.kt`, написан вручную.

**Цикл агента** (максимум 10 итераций):

1. Отправить в Ollama историю сообщений и описание инструментов.
2. Если в ответе нет `tool_calls`, это финальный ответ: вывести его и токены, завершить.
3. Иначе выполнить каждый вызов инструмента, добавить результат в историю как сообщение `role: tool` и вернуться к шагу 1.

**Инструменты** (идея из README: удалённые команды и состояние парка):

| Инструмент | Что делает | Вызов симулятора |
|---|---|---|
| `list_robots` | список роботов: id, состояние, заряд, ошибка | `GET /robots` |
| `send_command(robot_id, command)` | команда `START` / `PAUSE` / `RESUME` / `ABORT` / `RETURN_HOME` | `POST /robots/{id}/commands` |

Системный промпт: ассистент оператора парка, сначала смотреть состояние (`list_robots`), потом действовать, отвечать по-русски кратко.

Недопустимые команды отклоняет сам симулятор (`ILLEGAL_STATE`, см. FSM в README), агент только передаёт ответ модели.

## 4. Лог работы агента

Запросы выполнялись по одному (один запуск = один запрос). Состояние роботов в симуляторе сохранялось между запросами.

### Запрос 1. «Что с парком?»

```
🔧 [0] list_robots {} -> [{"id":"cleanbot-01","state":"IDLE","battery":100,...},{"id":"cleanbot-02","state":"IDLE","battery":100,...},{"id":"cleanbot-03","state":"IDLE","battery":100,...}]
🤖 Всё в порядке: все роботы в состоянии IDLE, заряд 100%. Ошибок нет.
tokens: in=738 out=46
```

### Запрос 2. «Запусти уборку у cleanbot-01»

```
🔧 [0] list_robots {} -> [... все три в IDLE ...]
🔧 [1] send_command {"robot_id":"cleanbot-01","command":"START"} -> {"accepted":true,"requestId":"2030c0b4-...","reason":null}
🤖 Уборка запущена для cleanbot-01.
tokens: in=1276 out=62
```

### Запрос 3. «Поставь на паузу всех, кто сейчас убирает»

```
🔧 [0] list_robots {} -> [{"id":"cleanbot-01","state":"CLEANING","battery":84,...},{"id":"cleanbot-02","state":"IDLE",...},{"id":"cleanbot-03","state":"IDLE",...}]
🔧 [1] send_command {"robot_id":"cleanbot-01","command":"PAUSE"} -> {"accepted":true,"requestId":"f369ef1f-...","reason":null}
🤖 Робот CleanBot 01 теперь на паузе. Остальные находятся в режиме ожидания.
tokens: in=1288 out=77
```

Агент сам выбрал из списка единственного робота в состоянии `CLEANING`.

### Запрос 4. «Продолжи уборку у cleanbot-02» (недопустимая команда)

```
🔧 [0] list_robots {} -> [{"id":"cleanbot-01","state":"PAUSED",...},{"id":"cleanbot-02","state":"IDLE","battery":100,...},...]
🔧 [1] send_command {"robot_id":"cleanbot-02","command":"RESUME"} -> {"accepted":false,"requestId":"289c0e9d-...","reason":"ILLEGAL_STATE"}
🤖 Уборка у cleanbot-02 уже включена. Невозможно продолжить.
tokens: in=1278 out=71
```

Симулятор корректно отклонил команду: `RESUME` допустима только из `PAUSED`, а робот в `IDLE`. Агент верно сообщил, что команда не выполнена, но **неверно объяснил причину**: робот не «уже убирает», он простаивает (см. раздел 7).

### Запрос 5. «Отправь cleanbot-01 домой»

```
🔧 [0] send_command {"robot_id":"cleanbot-01","command":"RETURN_HOME"} -> {"accepted":true,"requestId":"824476f5-...","reason":null}
🤖 Команда отправлена: cleanbot-01 возвращается домой.
tokens: in=713 out=52
```

Модель пропустила `list_robots` и сразу отправила команду, так как id был назван в запросе.

|---|---|---|---|---|---|
| 1 | Что с парком? | 1 | 738 | 46 | 784 |
| 2 | Запусти уборку у cleanbot-01 | 2 | 1276 | 62 | 1338 |
| 3 | Поставь на паузу всех, кто убирает | 2 | 1288 | 77 | 1365 |
| 4 | Продолжи уборку у cleanbot-02 | 2 | 1278 | 71 | 1349 |
| 5 | Отправь cleanbot-01 домой | 1 | 713 | 52 | 765 |
| | **Итого** | 8 | **5293** | **308** | **5601** |

Стоимость: **0** (локальная модель). Токены берутся из полей `prompt_eval_count` и `eval_count` ответов Ollama и суммируются по всем итерациям цикла.

## 6. Проблемы по ходу работы

| Проблема | Причина | Решение |
|---|---|---|
| Ответ «Я не понимаю вопрос» на первый запрос | Рассинхрон кодировок: консоль Windows (CP866) и JVM (CP1251), модель получила искажённый текст | `chcp 65001`, UTF-8 для `[Console]` и `-Dfile.encoding=UTF-8` в `jvmArgs` |
| `ReadAfterEOFException` | Gradle по умолчанию не передаёт stdin задаче `run` | `standardInput = System.in` в `agent/build.gradle.kts` |
| `ConnectException: Connection refused` | Симулятор не работал: `gradlew --stop` остановил Gradle-демон вместе с ним | Перезапустить симулятор, не вызывать `--stop` при работающем сервере |
| Gradle: «Java 8 JVM» | В новой консоли не был задан `JAVA_HOME` | Установить JDK 17 и задать `JAVA_HOME` постоянно |

## 7. Наблюдения

- **Рабочая цепочка.** Модель на 4B параметров надёжно выбирает инструмент и подставляет аргументы (id робота, команда из enum) во всех пяти запросах. Ошибок формата вызова не было.
- **Планирование.** В запросе 3 агент сам отобрал нужного робота по состоянию из `list_robots`: получилась цепочка «посмотреть, затем действовать».
- **Слабое место: объяснение отказов.** В запросе 4 модель выдумала причину («уже включена»), хотя в данных было `state: IDLE` и `reason: ILLEGAL_STATE`. Для надёжного управления причину отказа лучше передавать оператору как есть или добавить в системный промпт правило: «при `accepted:false` назови `reason` и текущее состояние робота».
- **Пропуск `list_robots`.** В запросе 5 модель не проверила состояние перед командой. Для безобидных команд это допустимо, для рискованных нужна проверка в коде.
- **Рост токенов.** Каждая итерация заново отправляет всю историю, поэтому запрос с двумя вызовами стоит ≈1280 входных токенов против ≈710–740 для одного вызова. На платных API это влияло бы на цену, при локальной модели только на время ответа.
- **Безопасность.** Решение о команде принимает модель, а допустимость независимо проверяет симулятор по FSM, поэтому ошибка модели не приводит к недопустимому переходу.

## 8. Ответы на вопросы задания

> Вставьте сюда вопросы из методички и ответы. Ниже заготовки по типичным вопросам.

**Чем агент отличается от обычного запроса к модели?**
Агент работает в цикле: модель может вызвать инструмент, получить результат и продолжить с учётом реальных данных, пока не сформирует ответ. Обычный запрос завершается на первом ответе.

**Как модель узнаёт об инструментах?**
Описание инструментов (имя, описание, JSON-схема параметров) передаётся в поле `tools` каждого запроса. Модель сама решает, вызывать ли инструмент, и возвращает имя и аргументы в `tool_calls`, а выполняет вызов код агента.

**Почему выбрана локальная модель?**
Бесплатно, не нужны ключи и сеть, данные остаются на машине. Цена: ограничения качества, например слабое объяснение причин отказов (раздел 7).

**Что можно улучшить?**
Добавить инструменты расписаний и статистики, подтверждение рискованных команд человеком, передачу `reason` без пересказа моделью, более сильную модель (например, qwen3:8b).
