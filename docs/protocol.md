# Протокол обмена simulator ↔ app

База: `http://<host>:8080` (REST), `ws://<host>:8080` (WebSocket).
Порт задаётся переменной окружения `SIMULATOR_PORT` при запуске (по умолчанию `8080`).

## WebSocket: телеметрия

`GET /telemetry`

Раз в ~1 секунду сервер присылает JSON-**массив** телеметрии по всем роботам сразу
(расширение относительно README: батч вместо одного объекта — меньше сообщений,
проще собрать список на клиенте одним `decode`):

```json
[
  {
    "robotId": "cleanbot-01",
    "timestamp": "2026-09-05T14:32:11Z",
    "state": "CLEANING",
    "battery": 63,
    "progress": 0.42,
    "position": { "x": 12, "y": 4 },
    "error": null
  },
  { "robotId": "cleanbot-02", "...": "..." }
]
```

`state` ∈ `IDLE | CLEANING | PAUSED | RETURNING | CHARGING | ERROR`
`error` ∈ `null | STUCK | BRUSH_JAMMED | TANK_FULL | SENSOR_FAULT | LOW_BATTERY`

## REST

| Метод | Путь | Описание |
|---|---|---|
| GET | `/robots` | список роботов (id, name, state, battery, error) |
| GET | `/robots/{id}` | сводка по одному роботу |
| POST | `/robots/{id}/commands` | команда роботу |
| GET | `/robots/{id}/schedules` | текущее расписание |
| PUT | `/robots/{id}/schedules` | заменить расписание целиком (ошибка валидации → 400 с текстом; неизвестный робот → 404) |
| GET | `/robots/{id}/plan` | текущий план уборки |
| PUT | `/robots/{id}/plan` | заменить план целиком (ошибка валидации → 400 с текстом) |
| GET | `/robots/{id}/sessions?from&to` | история сессий (ISO-8601, оба параметра опциональны) |
| GET | `/robots/{id}/logs` | журнал событий, новые сверху |
| GET | `/robots/{id}/settings` | настройки робота |
| PUT | `/robots/{id}/settings` | обновить настройки (`robotId` в теле должен совпадать с id в пути, иначе 400) |

> Параметры `from`/`to` у `GET /robots/{id}/sessions` — ISO-8601, оба опциональны.
> Фильтр по времени **старта** сессии (`startedAt`), границы **включительные**:
> `from <= startedAt <= to`. При невалидной дате сервер вернёт 500 (`Instant.parse`),
> при неизвестном роботе — 404.

### План уборки

`GET /robots/{id}/plan` → `CleaningPlan`; `PUT /robots/{id}/plan` — замена целиком (по аналогии с расписанием).

```json
{
  "gridW": 20,
  "gridH": 14,
  "zones": [
    { "id": 1, "name": "Гостиная", "cells": [{ "x": 1, "y": 1 }, { "x": 2, "y": 1 }] },
    { "id": 2, "name": "Спальня", "cells": [{ "x": 9, "y": 4 }] },
    { "id": 3, "name": "Кухня", "cells": [{ "x": 2, "y": 9 }] }
  ]
}
```

- Сетка **фиксированная 20×14**; координаты телеметрии `position {x, y}` — целые, маппятся 1:1 на клетку.
- Координаты клеток 0-based: `0 <= x < gridW`, `0 <= y < gridH`.
- Валидация на PUT (ошибки → 400, тело — plain-text с причиной; неизвестный робот → 404):
  - `gridW`/`gridH` должны быть ровно `20`/`14`;
  - клетки в границах сетки;
  - клетки без дублей (в том числе **между** зонами);
  - зона ≥ 1 клетки.
- Успешный PUT возвращает 200, пишет запись в журнал робота и применяется при **следующем START** — текущая уборка не прерывается.
- Дефолтный план у каждого робота — 3 зоны (генерируется при старте сервера).

### Расписание

`GET /robots/{id}/schedules` → список записей; `PUT /robots/{id}/schedules` — замена целиком (по аналогии с планом).

```json
{
  "entries": [
    { "id": "b1c2d3e4", "robotId": "cleanbot-01", "dayOfWeek": 1, "time": "06:00", "mode": "dry_sweep" },
    { "id": "e5f6a7b8", "robotId": "cleanbot-01", "dayOfWeek": 3, "time": "06:00", "mode": "wet_mopping" }
  ]
}
```

- `dayOfWeek` ∈ `1..7` (ISO-8601, понедельник = 1);
- `time` — строка `"HH:mm"` (часы `00–23`, минуты `00–59`);
- `mode` ∈ `dry_sweep | wet_mopping`;
- `robotId` каждой записи должен совпадать с `id` в пути (иначе запись запустила бы уборку чужого робота).

Валидация на PUT (ошибки → 400, тело — plain-text с причиной; неизвестный робот → 404).
Успешный PUT возвращает 200. Расписания реально запускают уборку (см. «Автозапуск по расписанию»), поэтому все поля проверяются.

### Команды

`POST /robots/{id}/commands`
```json
{ "command": "PAUSE", "requestId": "b1c2d3e4" }
```
`command` ∈ `START | PAUSE | RESUME | ABORT | RETURN_HOME | RESET`

> `RESET` — дополнение к README: сбрасывает робота из `ERROR` в `IDLE`.
> Переход `ERROR --reset--> IDLE` уже был в таблице FSM в README, но не был
> явно перечислен как REST-команда — без него инженерное меню не может
> восстановить робота после аварии.

Ответ:
```json
{ "accepted": true, "requestId": "b1c2d3e4" }
```
или
```json
{ "accepted": false, "requestId": "b1c2d3e4", "reason": "ILLEGAL_STATE" }
```
`reason` ∈ `ILLEGAL_STATE | UNKNOWN_COMMAND`; кроме того, `START` с пустым планом
(нет зон или все зоны без клеток) отклоняется до проверки FSM с `reason: "План не задан"`.

### Конечный автомат (таблица переходов из README, без изменений)

| Состояние | Событие | Следующее состояние | Источник события |
|---|---|---|---|
| `IDLE` | `start` | `CLEANING` | REST-команда |
| `IDLE` | `return_home` | `RETURNING` | REST-команда |
| `CLEANING` | `pause` | `PAUSED` | REST-команда |
| `PAUSED` | `resume` | `CLEANING` | REST-команда |
| `CLEANING`/`PAUSED` | `abort`/`return_home` | `RETURNING` | REST-команда |
| `RETURNING` | `docked` | `CHARGING` | внутреннее (позиция == станция) |
| `CHARGING` | `battery_full` | `IDLE` | внутреннее (заряд == 100%) |
| любое кроме `ERROR` | `fault` | `ERROR` | внутреннее (случайная авария) |
| `ERROR` | `reset` | `IDLE` | REST-команда |

Недопустимая в текущем состоянии команда отклоняется с `reason: "ILLEGAL_STATE"`.

## Симуляция (что происходит "под капотом")

- Тик каждого робота — раз в секунду.
- **Автозапуск по расписанию**: раз в 15 секунд сервер сверяет текущие день недели и время
  (**локальная таймзона сервера**) с расписаниями роботов; совпавшая запись стартует уборку
  (`mode` из записи), если робот в `IDLE` (иначе — запись в журнал «пропущено»).
  Несколько записей в одну минуту: каждая получает свою попытку старта (не-IDLE/пустой план
  → «пропущено» в журнале). Повторное срабатывание в ту же минуту подавляется.
- В `CLEANING`: заряд -1%/тик. Движение по маршруту «змейкой» по клеткам зон плана
  (зона за зоной, в зоне — по строкам со сменой направления), один шаг сетки за тик,
  `progress` = доля пройденных клеток маршрута. Старт с пустым планом отклоняется
  на POST commands (`reason: "План не задан"`), поэтому «блуждания без плана» нет.
  Авария завершает сессию как aborted=true.
- При заряде ≤15% — принудительный `RETURNING` (сессия помечается `aborted=true`).
- При прогрессе 100% — `RETURNING` (сессия `aborted=false`).
- Шанс аварии ~1%/тик в `CLEANING` → случайный код ошибки (кроме `LOW_BATTERY`).
- В `RETURNING`: пошаговое движение к точке стыковки `(0,0)`.
- В `CHARGING`: заряд +3%/тик до 100%.
- При старте сервера для каждого робота генерируется ~40 сессий за последний месяц
  (для экрана статистики) — при перезапуске история сбрасывается и генерируется заново.
